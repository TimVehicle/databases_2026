#### Q1 (Уникальные рейсы и сортировка)

 > Чем поведение `SELECT DISTINCT flight_no FROM flights ORDER BY flight_no` отличается от `SELECT flight_no FROM flights GROUP BY flight_no ORDER BY flight_no`? Может ли результат выполнения этих запросов когда-либо различаться с точки зрения физического плана выполнения (`EXPLAIN`) или итогового набора данных?
---
```sql
SELECT DISTINCT flight_no
FROM flights
ORDER BY flight_no;
```

```sql
SELECT flight_no
FROM flights
GROUP BY flight_no
ORDER BY flight_no;
```

`DISTINCT` предназначен именно для удаления дубликатов, а `GROUP BY` формирует группы строк с одинаковым `flight_no`

В данном случае агрегатные функции для `GROUP BY` не используются(а для `DISTINCT` невозможны в любом случае), поэтому фактически каждая группа превращается в одно значение `flight_no`

С точки зрения итоговых данных *конкретно в этом случае* запросы одинаковы, но с точки зрения физического плана могут различаться и выполняться PostgreSQL по разному
> [!NOTE]
> Стоит упомянуть также что `GROUP BY` в логическом порядке выполняется раньше 

> Почему для получения упорядоченного списка рейсов достаточно использовать только `ORDER BY flight_no`, не добавляя явно `ASC`? Что произойдет со строками, у которых `flight_no` содержит символы нижнего и верхнего регистра (например, 'PG0001' и 'pg0001') при сортировке по умолчанию в PostgreSQL?
---

По умолчанию в PostgreSQL сортировка выполняется от меньшего к большему — ASCEND(возвышение), поэтому явно задавать порядок нужно только в обратном случае DESC

Как регистр повлияет на сортировку определяется согласно правилам `collation`, применяемой к этим значениям, которые едины для всей БД и определяются согласно системе во время ее создания, если конечно они не указаны явно

Узнать текущий `collation` можно следующим образом:
```sql
SELECT datname, datcollate, datctype
FROM pg_database
WHERE datname = current_database();
```

Пример вывода
```
  datname   | datcollate |  datctype
------------+------------+------------
 project_db | en_US.utf8 | en_US.utf8
```

#### Q2 (Аэропорты и выручка за билеты)

>Предположим, один и тот же пассажир покупает два разных билета на один и тот же рейс (разные места). Как ваш запрос, считающий суммарную выручку (`SUM(amount)`) и количество пассажиров на рейс, учитывает такие записи? Не происходит ли двойного счета пассажиров при использовании `COUNT(*)`?
---

При использовании `COUNT(amount)` & `COUNT(*)` "пассажир" и сумма билета будет учтена за каждую запись в базе данных вместе с дубликатами

Чтобы исключить повторяющихся пассажиров нужно использовать 
```sql
COUNT(DISTINCT passenger_id)
```


 >Что делает ваш запрос, если рейс существует в таблице `flights`, но в таблице `ticket_flights` для него нет ни одного проданного билета? Какой тип соединения (`JOIN`) следует использовать, чтобы такой рейс попал в итоговую выборку с нулевой выручкой, и почему `INNER JOIN` здесь не подойдет?
---

Если рейс есть в  `flights`, но для него нет записей `ticket_flights`, то `INNER JOIN` выкинет эти значения

Необходим `LEFT JOIN`
```sql
FROM flights f
LEFT JOIN ticket_flights tf
    ON f.flight_id = tf.flight_id
```

Тогда все рейсы из `flights` сохранятся, а для рейса без билетов значения из второй таблицы будут NULL, что в свою очередь надо будет учитывать при агрегате
```sql
COALESCE(SUM(tf.amount), 0)
```

`COALESCE` возвращает первое значение, которое не является NULL, а при `tf.amount` = NULL `SUM(NULL)` вернет NULL
#### Q3 (Отмененные рейсы и города)

>В задании сказано: «найти города, из которых ни один рейс не был отправлен со статусом 'Cancelled'». Как ваш запрос учитывает ситуацию, когда в таблице `airports` есть аэропорт, который вообще не фигурирует в таблице `flights`? Должен ли такой город попасть в результат, и как этого добиться (используя `NOT IN` или `NOT EXISTS`)?
---

Такой город должен учитываться, т.к. если рейсов из него не было вовсе, то их и не отменяли

Предпочтительный запрос (объяснение в следующем пункте)
```sql
SELECT a.city
FROM airports a
WHERE NOT EXISTS (
    SELECT 1
    FROM flights f
    WHERE f.departure_airport = a.airport_code
      AND f.status = 'Cancelled'
);
```

 >Поле `status` в таблице `flights` может содержать `NULL` (например, если рейс еще в плане). Как ваш запрос избегает классической ловушки `NOT IN` с `NULL`? Объясните, почему `city NOT IN (SELECT departure_airport ... WHERE status = 'Cancelled')` может вернуть пустой результат, если подзапрос вернет хотя бы один `NULL`, и почему `NOT EXISTS` этой проблемы лишен.
---

`NOT IN` может некорректно работать, если подзапрос возвращает хотя бы один `NULL`

Например
```sql
SELECT a.city
FROM airports a
WHERE a.airport_code NOT IN (
    SELECT f.departure_airport
    FROM flights f
    WHERE f.status = 'Cancelled'
);
```

Если подзапрос вернул
```text
MOW //Moscow
LED //Leningrad
NULL
```

то для аэропорта `ABC` PostgreSQL фактически проверяет
```text
ABC <> MOW
AND 
ABC <> LED
AND 
ABC <> NULL
```

Сравнение с `NULL` даёт `UNKNOWN`, поэтому всё условие также становится `UNKNOWN`, а `WHERE` оставляет только `TRUE`. В результате запрос не вернет ни одного города

Поэтому для такой задачи безопаснее использовать `NOT EXISTS`

`NOT EXISTS` проверяет, существует ли конкретный отменённый рейс для данного аэропорта. Если подходящей строки нет, условие выполняется, даже если в других строках встречается `NULL`

Если `status = NULL`, условие `status = 'Cancelled'` также не является `TRUE`, поэтому такой рейс не считается отменённым

Для каждого случая логика такая
 - есть отменённый рейс → `EXISTS` = `TRUE` → `NOT EXISTS` = `FALSE` → аэропорт исключается
 - нет отменённых рейсов → `NOT EXISTS` = `TRUE` → аэропорт остается
 - вообще нет рейсов  → `NOT EXISTS` = `TRUE` → аэропорт остается

#### Q4 (Места на борту и дубликаты)

 >При посадке на рейс (`boardings`) один и тот же пассажир (`passenger_id`) может ошибочно получить два посадочных талона на разные места. Как в вашем запросе (если требуется вывести уникальные пассажиры на рейсе) предотвращается дублирование строк? Что эффективнее использовать здесь: `DISTINCT` или `GROUP BY`, и как это отразится на плане выполнения?

Если один пассажир (`passenger_id`) ошибочно получил два посадочных талона на разные места, обычный `JOIN` вернёт две строки для одного пассажира

Если требуется вывести уникальных пассажиров, можно использовать 
```sql
SELECT DISTINCT passenger_id
FROM boardings;
```
или
```sql
SELECT passenger_id
FROM boardings
GROUP BY passenger_id;
```

В данном случае результат будет одинаковым

Нельзя сказать, что `DISTINCT` всегда эффективнее `GROUP BY` или наоборот. PostgreSQL сам выбирает способ выполнения запроса

Конкретный план можно посмотреть с помощью
```sql
EXPLAIN ANALYZE ...
```

Для простого получения уникальных пассажиров логичнее использовать `DISTINCT`, а разница в производительности зависит от данных и выбранного PostgreSQL плана выполнения

 >Если пассажир сдал билет (его нет в `ticket_flights`), но успел получить посадочный талон (есть в `boardings`), как ваш запрос обработает эту аномалию данных при `JOIN` таблиц `tickets` и `boardings`? Окажется ли этот пассажир в списке пассажиров рейса? 

Если пассажир отсутствует в `ticket_flights`, но его посадочный талон есть в `boardings`, то при `INNER JOIN` такой пассажир не попадёт в результат
```sql
FROM ticket_flights tf
INNER JOIN boardings b
    ON tf.ticket_no = b.ticket_no
```

Здесь остаются только те строки, для которых есть соответствие в обеих таблицах. Поэтому отсутствие билета означает, что соответствующей пары для посадочного талона нет

Если нужно обнаружить такие аномальные записи, можно использовать `LEFT JOIN` со стороны `boardings`
```sql
FROM boardings b
LEFT JOIN ticket_flights tf
    ON tf.ticket_no = b.ticket_no
WHERE tf.ticket_no IS NULL;
```

Так можно получить посадочные талоны, для которых нет соответствующего билета.

Следовательно, при обычном `INNER JOIN` пассажир с посадочным талоном, но без записи в `ticket_flights`, не окажется в списке пассажиров рейса.
#### Q5 (DDL и блокировки на живой таблице)

 >Вы выполняете команду `ALTER TABLE flights ADD COLUMN weather_data JSONB;` на нагруженной production-таблице. За секунду до этого другой пользователь начал долгую аналитику: `BEGIN; SELECT COUNT(*) FROM flights;`. Что произойдет с вашей DDL-командой? Какую блокировку она попытается наложить и почему ей придется ждать завершения `SELECT`?

Команда
```sql
ALTER TABLE flights ADD COLUMN weather_data JSONB;
```
попытается получить блокировку `ACCESS EXCLUSIVE` на таблицу `flights`

`SELECT` обычно получает блокировку `ACCESS SHARE`. Эти блокировки конфликтуют
```text
SELECT       → ACCESS SHARE
ALTER TABLE  → ACCESS EXCLUSIVE
```

Согласно принципу *Isolation (I)* из ACID параллельные транзакции должны быть изолированы друг от друга. В PostgreSQL это, в частности, обеспечивается механизмом блокировок. Поэтому DDL-команда будет ждать завершения транзакции, даже если сам `SELECT COUNT(*)` уже выполнился, поскольку транзакция всё ещё удерживает блокировку таблицы до `COMMIT` или `ROLLBACK`

 >Вам нужно добавить колонку `is_delayed BOOLEAN DEFAULT false;` в таблицу `flights` на PostgreSQL 11+. Почему в современных версиях это выполняется мгновенно, не переписывая таблицу? Опишите, как PostgreSQL хранит значение по умолчанию в системном каталоге, и что произойдет с параллельными `INSERT`, если впоследствии изменить этот `DEFAULT` на `true`?

В PostgreSQL 11+ добавление колонки с постоянным значением `DEFAULT` может выполняться без полного переписывания таблицы
```sql
ALTER TABLE flights
ADD COLUMN is_delayed BOOLEAN DEFAULT false;
```

PostgreSQL сохраняет значение `DEFAULT` в системном каталоге и использует его как логическое значение по умолчанию для старых строк, которым физически не требуется сразу записывать новое значение в каждую строку

Поэтому PostgreSQL не должен проходить по всей таблице и переписывать все существующие строки, что делает такую операцию практически мгновенной даже для большой таблицы

При добавлении новых строк `DEFAULT` используется обычным образом
```sql
INSERT INTO flights (...)
VALUES (...);
```

Если затем изменить значение по умолчанию
```sql
ALTER TABLE flights
ALTER COLUMN is_delayed SET DEFAULT true;
```

то новый `DEFAULT` будет применяться к *последующим* `INSERT`

Уже существующие строки при этом автоматически не изменятся: их значение останется `false`

Параллельные `INSERT`, которые выполняются после изменения `DEFAULT`, будут использовать уже новое значение `true`

Т.е. изменение `DEFAULT` не означает массовое обновление уже существующих строк.

>Вы решили построить индекс для ускорения поиска: `CREATE INDEX idx_flights_status ON flights(status);`. Почему эта команда «подвесит» все `UPDATE` и `INSERT` в таблицу на время построения? Какой синтаксис нужно использовать, чтобы база данных продолжила работать без блокировок на запись, и в чем будет компромисс (почему так делают не всегда)?

Команда
```sql
CREATE INDEX idx_flights_status
ON flights(status);
```
получает блокировку `SHARE`, которая конфликтует с блокировками, необходимыми для изменения таблицы

Поэтому на время построения индекса обычный `CREATE INDEX` блокирует операции изменения данных (`INSERT`, `UPDATE`, `DELETE`) в таблице `flights`

Чтобы создать индекс без блокировки записи, используется
```sql
CREATE INDEX CONCURRENTLY idx_flights_status
ON flights(status);
```

`CONCURRENTLY` позволяет продолжать выполнять `INSERT`, `UPDATE` и `DELETE` во время построения индекса

Однако у этого подхода есть компромиссы
- индекс строится дольше
- требуется больше ресурсов
- выполняется несколько проходов по таблице
- операция сложнее с точки зрения транзакций
- `CREATE INDEX CONCURRENTLY` нельзя выполнять внутри обычной транзакции
- при ошибке может остаться невалидный индекс, который потребуется удалить или перестроить.

Поэтому на production-таблицах `CONCURRENTLY` часто используют, когда важно не останавливать операции записи, а обычный `CREATE INDEX` выбирают, когда допустимо временно блокировать изменения ради более быстрого и простого построения индекса.

#### Q6 (Агрегация и NULL в вычислениях)

 >Вам нужно вычислить среднюю задержку рейса как `AVG(actual_departure - scheduled_departure)`. Что произойдет с результатом агрегации, если для некоторых рейсов поле `actual_departure` равно `NULL` (рейс отменен)? Исключит ли `AVG` эти строки из расчета, и как это повлияет на итоговое среднее значение?

Если выполнить
```sql
SELECT AVG(actual_departure - scheduled_departure)
FROM flights;
```
и для некоторых рейсов `actual_departure` равно `NULL`, то результат выражения `actual_departure - scheduled_departure` для таких строк также будет `NULL`

`AVG` игнорирует значения `NULL` и не учитывает такие строки при расчёте среднего

 >В таблице `flights` есть колонка `aircraft_code`. Если вы выполните `SELECT COUNT(aircraft_code) FROM flights`, а затем `SELECT COUNT(*) FROM flights`, будут ли результаты одинаковыми? В каком случае они могут различаться, и как это связано с ограничением `NOT NULL` на уровне схемы таблицы?

Результаты
```sql
SELECT COUNT(aircraft_code)
FROM flights;
```
и
```sql
SELECT COUNT(*)
FROM flights;
```
будут одинаковыми только в том случае, если `aircraft_code` не содержит `NULL`

Разница заключается в том, что
- `COUNT(*)` считает все строки таблицы
- `COUNT(aircraft_code)` считает только строки, где `aircraft_code` не равен `NULL`.

Если же был задан 
```sql
aircraft_code TEXT NOT NULL
```
то ` COUNT(aircraft_code)` посчитает все строки, как и `COUNT(*)`
